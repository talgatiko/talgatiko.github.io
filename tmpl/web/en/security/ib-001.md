# ИБ-001. BDSM-InfoSec: Security That Punishes Users for Someone Else’s Architecture

[Все статьи / All articles](https://talgatiko.github.io/en/security/) · [Русский](https://talgatiko.github.io/ru/security/ib-001/) · [English](https://talgatiko.github.io/en/security/ib-001/)

## A Manifesto for Respecting People’s Memory, Secrets, and Time

A user comes to a system to get something done: buy a product, write an email, talk to a customer, update a CRM record. First, though, they must invent yet another password, comply with rules about uppercase letters and special characters, install an application, start a VPN, and learn to respond correctly to warnings.

When a service’s database leaks, the discussion too often comes down to how well the user performed their part of this ritual. Yet they were not the one who chose the server, the access architecture, or the storage method.

I call this practice BDSM-InfoSec: security consumes people’s memory and attention as a free corporate resource. The harshness is deliberate. When a system spends years teaching people to tolerate pointless obstacles, polite wording does not always convey the problem.

> Stop treating inconvenience as evidence of security.

## The User Is Not a Free Hardware Security Module

People are poor at generating randomness, forget secrets they rarely use, and make mistakes in repetitive tasks. These are the starting conditions for design. A demand that people never make mistakes does not change those conditions.

A warning shown too often teaches people to look for the “Continue” button. Banning a convenient tool creates a workaround. One more client that conflicts with other software gives people one more reason to disable protection so they can work.

Security fatigue is studied as a real problem in user behavior. A slogan telling people to “pay more attention” will not eliminate it. [NIST: Security Fatigue](https://csrc.nist.gov/pubs/journal/2016/09/security-fatigue/final)

## Compare Against the System People Actually Live With

People reuse passwords. Websites receive those passwords and store them in different ways. Developers are issued keys with excessive privileges, then told never to publish them. Corporate applications are exposed to the internet, and attackers are blocked as they are noticed.

Against this background, a proposal to reduce the consequences of a mistake often meets the objection: “But your solution can be attacked too.”

It can. So we need to ask: what could the attacker do before, what will they still be able to do after the change, and how much work will the person have to do?

If a dishonest website previously received the password itself and now has to guess it, that is an improvement. If a stolen value previously granted immediate access to other websites and now works directly on only one, that is an improvement. The remaining threats do not erase the difference.

None of the ideas below removes the need for TLS, secure server-side storage, application permissions, limits on attempts, or infrastructure protection. Those layers remain. A user’s memory and unfailing accuracy should not have to serve as the last defense against defects in every other layer.

## A User’s Secret Should Not Become Every Website’s Property

A person does not need a new memory slot for every service. A trusted client can use one personal secret to derive different service-specific values. The website then never receives the original password, and a leaked service-specific value ceases to be a ready-made key to all the other websites.

This is no license to store data carelessly. Protecting the server remains the service’s responsibility. Part of the protection simply no longer depends on how trustworthy the next website happens to be.

Details: [service-specific passwords](https://talgatiko.github.io/en/security/ib-002/).

## Most Services Do Not Need a Separate Password

Most services do not need a separate password. Passwords should be an optional means of access. A service can send a one-time link through a personal communication channel, and the user can follow it to sign in without creating, and later recovering, yet another password. Access through links sent to users is already used in many places.

I consider access through a one-time link sent via a personal communication channel a better solution than signing in with a password. Users do not have to create another permanent secret for yet another website. This is a fully fledged means of access; treating it as a simplified compromise assumes from the outset that a password must be the norm.

If additional protection is needed, or you do not trust the provider of one communication channel, require confirmation through two channels. Protection can be strengthened without making a password mandatory again.

Details: [one-time links and confirmations](https://talgatiko.github.io/en/security/ib-003/).

## Proof of Sign-In Does Not Have to Be a Permanent Password

A trusted client can reconstruct a service-specific key and send a temporary code or a response to a one-time challenge. The user performs a familiar action, while an intercepted proof does not become a long-lived access pass.

These schemes offer different protection when server data leaks and impose different recovery requirements. Engineers need to account for those differences without automatically turning them into new duties for the user.


## Development Does Not Need Production Secrets for Everyday Work

If publishing an ordinary test example exposes customer data or grants control over production resources, dangerous privileges were issued before publication ever happened.

Developers should work in a restricted environment. Infrastructure issues a production identity to a process authorized to run in production. Secret scanning is useful as a safeguard, but it does not replace the separation of privileges.

The aim is to limit the consequences of an expected human mistake and make recovery from it possible.

Details: [development capabilities](https://talgatiko.github.io/en/security/ib-004/).

## Network Admission Does Not Necessarily Require a New Client

“Tower on the Shore” was implemented. A user opened a different page and entered their existing CRM credentials. The system allowed their observed IP address through the network filter, after which work traffic flowed directly. There was no need to install a VPN for every employee.

Core services became less accessible from arbitrary external addresses, while application authentication remained in place. This illustrates how an infrastructure change can provide protection while leaving the user’s workflow almost unchanged.

Details of the implemented solution and proposals for its further development: [“Tower on the Shore”](https://talgatiko.github.io/en/security/ib-005/).

## Ask What Changed for the Attacker

Before introducing a control, answer six questions:

1. Which specific capability does it take away from the attacker?
2. Which real existing practice are we comparing it against?
3. Could the same result be achieved automatically?
4. What happens when someone makes an ordinary human mistake?
5. Will the inconvenience drive people toward a more dangerous workaround?
6. What supports the claimed improvement: a measurement, a property of the algorithm, or, for now, only an assumption?

Current guidance already rejects mandatory password composition rules and arbitrary periodic password changes, and supports password managers and convenient entry. The gap between sensible guidance and everyday practice is part of the problem, not a justification for that practice. [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)

Additional confirmation is sometimes necessary. But the attention it consumes should have a clear protective value. Users should not have to compensate for architectural defects by remaining infallible for the rest of their lives.

> Respect the user’s secret. Respect their time. Respect the memory slots in their head.
>
> Security should be a property of the system, not a punishment for using it.
