# ИБ-002. Different passwords: why was this job assigned to a person?

[Все статьи / All articles](https://talgatiko.github.io/en/security/) · [Русский](https://talgatiko.github.io/ru/security/ib-002/) · [English](https://talgatiko.github.io/en/security/ib-002/)

This article continues the [manifesto against BDSM InfoSec](https://talgatiko.github.io/en/security/ib-001/).

Alice opens a shop's website. Create a complex password. Never use it anywhere else. Add a special character. Now do the same on the forum and in the work application. Alice has a head, not a branch of the passport office, but that is her problem now.

Alice reuses one memorable password. After a leak, someone explains that the user is the weakest link and should have paid more attention to the security lecture.

Who decided that human memory should invent and store different passwords for computers?

## The site receives more than it needs

The shop, forum, and work system all receive Alice's complete password. A malicious forum need not even crack it: Alice has entered the very string it can immediately try on the shop.

The response is to tell the person to behave better. Remember more, do not reuse, do not forget. Responsibility for designing the login process quietly becomes the user's duty to train their memory. Then they are shamed for the predictable result.

This is what I call BDSM InfoSec: the department responsible for organizing protection turns the shortcomings of its own solution into a discipline test for everyone else.

## What I propose

The person remembers one underlying secret. Software transforms it according to the site and login: it sends one string to the shop and another to the forum. At the next login, it produces the same string for the same site and login.

Alice still enters her password. The computer prepares different values for different sites. The string received by the forum cannot simply be used on the shop. A similar transformation was already used in [PwdHash](https://crypto.stanford.edu/pwdhash/): assigning this work to software is entirely feasible.

Compare this with the practice described here: the person already reuses a password, and every site receives it in full. Guessing the underlying secret remains possible. But “try guessing it” and “here is my password” are different gifts to a malicious service.

## How adoption could begin

The minimal option is the site's own script. It transforms the password entered in the browser and sends a separate string to the server. I consider this an acceptable starting point, although an undesirable final arrangement: the site controls the script, can change it, and can take the original password. Here, the benefit depends on the site behaving honestly.

The preferred option is transformation in a browser, vetted extension, or operating-system manager outside the site's control. The page then receives only the string intended for it. This is one way to implement the central idea; specialists should choose the specific tool and arrange how it works.

## Whose job is it?

Those responsible for the login process and security must provide for password changes after a leak, account recovery, and access from another device. If Alice has to remember the transformation's internal settings to do any of this, the work has been handed straight back to the person it was meant to relieve.

A weak underlying password can still be guessed. If the underlying secret itself is exposed, the associated passwords must be changed. Device protection and server-side storage also remain the system's responsibilities. The proposal addresses a specific problem: it ends the direct reuse of one string across different sites.

Alice's job is to buy something or open her work application. The job of those organizing login is to let her do so without a collection of passwords in her head. Another lecture about her irresponsibility does not do that work.
